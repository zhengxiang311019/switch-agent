# Feature Specification: 工业协议通信分析

**Feature Branch**: `001-industrial-protocol-analysis`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "在交换机设备上设计工业协议 EtherNet/IP 和 PROFINET 分析软件，通过 ACL 将面板口报文复制到 CPU，分析经过交换机的 OT 业务数据，并可视化 OT 层通信的时延、抖动、丢包、超时、报文校验失败、流量统计和访问的业务内容分布。"

**Protocol scope update (2026-10-24)**: The passive decoder scope includes EtherNet/IP, PROFINET, Modbus TCP, OPC UA TCP, and MQTT. MQTT protocol inspection is distinct from the MQTT notification transport described in US5/FR-022. Decoder behavior follows protocol structure and field semantics documented by Wireshark dissectors; implementation is an independent bounded C parser, not linked/copied Wireshark source. TLS-protected or OPC UA encrypted application content is not decrypted.

## Product Reference Review

The [Indu-Sol PROFINET-INspektor NT product page](https://www.indu-sol.com.cn/index/product/view/id/33), reviewed on 2026-10-24, describes PROFINET real-time analysis, topology and asset management, port statistics, per-device jitter and refresh rate, self-learning alarm thresholds after acceptance, acceptance reports, time-server synchronization, event-triggered topology updates, topology quality coloring, and MQTT alarm actions. This feature adopts the passive-observation subset as user stories and requirements below. Active diagnostics or network scans are excluded because the product brief specifies ACL-copied traffic analysis and the analyzer must not inject or alter OT traffic. Port electrical leakage-current measurement is excluded because no such switch sensor capability was specified.

## Clarifications

### Session 2026-10-24

- Q: 希望交换机上保留多长时间的汇总通信指标和异常事件，供用户查看历史趋势？ → A: 默认保存最近 7 天；用户可以通过设置选择更长的保存时长。
- Q: 在交换机上，哪些用户应该能够查看 OT 分析结果并修改监测和保存设置？ → A: 沿用交换机现有账户体系；有查看权限的用户可以查看分析结果，只有管理员可以修改监测和保存设置。
- Q: MQTT 告警连接到消息代理时，应采用什么安全要求？ → A: 使用 TLS 加密并进行代理身份认证；凭据应安全保存，不在界面或日志中明文暴露。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看 OT 通信健康状况 (Priority: P1)

作为负责工业网络的工程师，我希望在交换机上看到 EtherNet/IP、PROFINET、Modbus TCP、OPC UA 和 MQTT 通信的实时概况和异常，以便快速判断 OT 通信是否正常并定位需要关注的设备或通信关系。

**Why this priority**: 首要价值是直接发现生产网络中的通信异常；协议流量总览和端点/通信关系视图构成可独立交付的最小可用能力。

**Independent Test**: 在已启用监测且有两种协议流量的网络中，工程师可分别查看协议、端点和通信关系的流量概况及异常状态，并能用一段已知流量验证展示结果。

**Acceptance Scenarios**:

1. **Given** 工程师已选择监测范围且交换机收到可识别的受支持协议报文，**When** 打开 OT 概览，**Then** 可按协议查看报文数、流量、通信端点和通信关系。
2. **Given** 某通信关系出现可识别的超时、丢包或校验异常，**When** 工程师查看该关系，**Then** 可看到异常类别、发生时间、涉及端点及统计数量。
3. **Given** 当前没有匹配的 OT 报文，**When** 工程师查看概览，**Then** 系统明确显示无匹配流量，而不把空数据呈现为正常通信。
4. **Given** 用户查看监测设置，**When** 修改汇总指标和异常事件的保存时长，**Then** 默认值为最近 7 天，且用户可以选择更长时长并查看当前设置。
5. **Given** 用户仅有查看权限，**When** 打开 OT 分析结果或监测设置，**Then** 用户可以查看结果和当前设置，但不能修改监测或保存设置；管理员可以修改这些设置。

### User Story 2 - 分析通信时延与异常 (Priority: P1)

作为运维工程师，我希望按通信关系查看时延、抖动、丢包、超时和校验失败的趋势与明细，以便区分持续性问题和短时异常。

**Why this priority**: 用户明确要求分析 OT 层往来通信质量指标；能按时间和通信关系追溯的指标比单一总量更有助于诊断。

**Independent Test**: 使用含已知请求/响应、缺失响应、重复或乱序报文以及可见校验错误的样本流量，检查对应趋势、事件和定义说明是否一致。

**Acceptance Scenarios**:

1. **Given** 一组可关联的请求和响应报文，**When** 工程师选择时间范围和通信关系，**Then** 可查看该往返通信时延及其随时间变化情况。
2. **Given** 同一通信关系在连续测量中时延有波动，**When** 工程师查看通信质量，**Then** 可查看抖动指标及其所覆盖的时间范围。
3. **Given** 在配置的响应等待时间内未观察到匹配响应，**When** 工程师查看异常，**Then** 系统记录超时事件，并将其与已确认丢包区分或标记为无法区分。
4. **Given** 捕获数据中能观察到报文校验错误，**When** 工程师查看异常统计，**Then** 可按协议、端点、通信关系和时间范围查看计数；不可见的校验错误不得报告为已确认错误或已确认无错误。

### User Story 3 - 了解业务类型和流量分布 (Priority: P2)

作为 OT 工程师，我希望了解各协议业务类别及其流量占比，以便识别主要业务、通信变化和未预期的访问活动。

**Why this priority**: 内容分布能帮助理解业务用途和流量变化；健康状态和通信质量异常是更紧急的首要场景。

**Independent Test**: 输入包含多类可识别 EtherNet/IP 和 PROFINET 业务的报文，确认类别、报文数、字节数、时间范围和占比能够按筛选条件查看。

**Acceptance Scenarios**:

1. **Given** 捕获流量中含可识别的协议服务或业务类别，**When** 工程师查看业务分布，**Then** 可按协议和业务类别查看报文数、流量及占比。
2. **Given** 某报文的业务类别无法识别或内容不可解码，**When** 工程师查看业务分布，**Then** 该流量归入明确的“未识别/不可解码”类别，不被错误归入已识别业务。
3. **Given** 工程师选择时间范围、协议或端点筛选条件，**When** 更新分布视图，**Then** 指标和占比基于相同筛选范围重新计算。

### User Story 4 - 查看 OT 拓扑和资产状态 (Priority: P2)

作为 OT 工程师，我希望查看从被动流量识别出的设备、端口和通信关系拓扑，并能按质量状态定位异常，以便理解异常设备在网络中的位置和关联。

**Why this priority**: 设备和拓扑上下文能缩短定位时间，但基础流量及通信质量仍是首要价值。

**Independent Test**: 使用包含可识别设备标识、交换机端口来源、通信关系和未知设备的样本流量，确认拓扑能呈现已观察实体与关系、端口统计和状态，并保留未知标识。

**Acceptance Scenarios**:

1. **Given** 交换机观察到 EtherNet/IP 或 PROFINET 设备及其通信，**When** 工程师查看拓扑，**Then** 系统按观测证据展示已识别设备、端口和通信关系，并对无法识别的实体明确标为未知。
2. **Given** 新设备首次出现或观察到控制器访问变化，**When** 分析器收到相关复制流量，**Then** 系统更新对应资产和拓扑信息，并记录触发事件。
3. **Given** 设备或关系具有通信质量数据，**When** 工程师查看拓扑，**Then** 系统以状态标记呈现健康、告警、确认异常或观测不完整，并提供文本/图标说明。
4. **Given** 平台提供端口状态和错误计数器，**When** 工程师查看设备/端口详情，**Then** 系统显示相应端口统计和数据来源；平台不提供时明确标为不可用。
5. **Given** 某设备存在可用的抖动样本，**When** 工程师查看该设备详情，**Then** 系统显示关联通信关系的抖动统计和样本覆盖范围，不把缺失样本显示为零。
6. **Given** 设备有可解析的周期性 PROFINET 通信和有效时间样本，**When** 工程师查看该设备详情，**Then** 系统显示观察到的刷新周期或刷新率；数据不足时标为不可用。

### User Story 5 - 建立通信基线并分发诊断结果 (Priority: P2)

作为 OT 管理员，我希望在验收或稳定运行阶段建立通信质量基线、获得告警阈值建议，并生成报告或将告警发送至监控系统，以便把本地诊断结果纳入运维流程。

**Why this priority**: 基线、报告和通知支持持续运维协作；实时查看和异常识别应先具备。

**Independent Test**: 对已完成观察窗口的样本，确认系统给出所选指标的阈值、可供管理员检查和调整，报告包含测量窗口及事件依据，且 MQTT 发送状态可见。

**Acceptance Scenarios**:

1. **Given** 管理员指定了基线观察窗口且窗口数据完整，**When** 基线采集完成，**Then** 系统根据观察到的质量指标生成告警阈值建议，管理员可检查和调整后启用。
2. **Given** 管理员请求生成某监测范围和时间窗口的诊断/验收报告，**When** 报告完成，**Then** 报告包含范围、时间、资产/拓扑摘要、质量指标、相关事件和观测完整性。
3. **Given** 管理员配置了 MQTT 告警目标且发生告警，**When** 系统发送通知，**Then** 消息包含事件类型、时间、关联设备/关系、可信状态和证据摘要，连接使用 TLS 且代理身份认证成功；TLS/认证/发送失败状态可见，凭据不在界面或日志中明文暴露。
4. **Given** 基线窗口数据不完整或观测负载受限，**When** 系统生成阈值建议，**Then** 建议标示数据不足，不会被静默启用。
5. **Given** 设备时间同步状态不稳定，**When** 工程师查看质量趋势、事件或报告，**Then** 系统显示时间状态并标记受影响数据。

### Edge Cases

- 交换机未收到镜像报文、监测范围未配置或当前时间范围内无匹配流量时，应显示相应状态，并避免将缺少观测误判为零异常。
- 报文被截断、格式无效、分片、重复、乱序或无法识别时，应保留可获得的基本流量统计，并将无法完成的协议解析或关联标记出来。
- 只看到通信单向流量时，不能生成需要双向请求/响应关联的往返时延；应明确标示数据不足。
- CPU 未能接收全部复制报文或观测负载达到能力边界时，应提示观测不完整，并避免把观测丢失直接认定为网络丢包。
- 采集时间范围内设备重启、时间基准变化或数据计数器重置时，应标示统计区间不连续。
- 校验错误只有在复制路径实际保留并暴露相应错误信息时才可计数；未被转发到 CPU 的坏帧不等于不存在校验错误。
- 设备身份或连接端口无法由观察数据确定时，应显示未知/低置信度，不得根据单一报文推断完整拓扑。
- 基线窗口出现镜像丢弃、时间同步不稳定或关键解析失败时，不得把所得阈值建议视为有效基线。
- MQTT 目标不可达时，应保留本地事件并显示通知失败，不能以发送失败覆盖原始异常状态。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 使用交换机指定监测端口送达 CPU 的复制流量作为分析输入，并允许用户查看监测范围和数据是否可用。
- **FR-002**: 系统 MUST 识别并分类可解析的 EtherNet/IP、PROFINET、Modbus TCP、OPC UA TCP 和 MQTT 流量，并为不能识别或不能完整解析的报文保留单独状态。加密的 MQTT/OPC UA 应用内容 MUST 分类为加密/不可见，不得伪称已解析。
- **FR-003**: 系统 MUST 按时间范围、协议、端点和通信关系展示报文数、字节数及流量趋势。
- **FR-004**: 系统 MUST 在双向报文可关联且时间信息可用时，提供通信往返时延及其变化情况；测量口径 MUST 在界面中说明。
- **FR-005**: 系统 MUST 提供抖动统计，并说明该统计所基于的时延样本范围和计算口径。
- **FR-006**: 系统 MUST 根据可观察的协议序列、通信关系或匹配响应缺失提供丢包与超时相关指标，并标明其判断依据及不确定性，不得将复制/观测损失直接认定为网络丢包。
- **FR-007**: 系统 MUST 统计捕获路径能够观察到的报文校验失败，并说明覆盖范围；无法观察时 MUST 明确标示不可用。
- **FR-008**: 系统 MUST 按所有受支持协议可识别的业务/服务类别呈现报文数、字节数和流量占比，并单独呈现未识别、加密或不可解码流量。
- **FR-009**: 系统 MUST 支持用户按时间范围、协议、端点及通信关系筛选概览、质量指标、异常事件和业务分布。
- **FR-010**: 系统 MUST 提供异常事件的时间、指标类型、涉及协议和端点/通信关系、统计值及数据可信状态，供用户追溯。
- **FR-011**: 系统 MUST 显示采集数据不足、监测不可用、解析不完整、计数器不连续或观测负载受限等影响结论的状态。
- **FR-012**: 系统 MUST 以业务类别和通信元数据实现业务分布分析；默认不展示或持久化 OT 应用层原始载荷内容。
- **FR-013**: 系统 MUST 允许用户配置超时判定所需的响应等待阈值，并在结果中显示使用的阈值。
- **FR-014**: 系统 MUST 默认保留最近 7 天的汇总通信指标和异常事件，并允许用户设置更长的保存时长；界面 MUST 显示当前保存时长。
- **FR-015**: 系统 MUST 使用交换机现有账户和权限；具有查看权限的用户 MUST 能查看 OT 分析结果及当前设置，只有管理员 MUST 能修改监测和保存设置。
- **FR-016**: 系统 MUST 基于被动观察到的设备、端口和通信关系呈现 OT 拓扑与资产视图，并保留设备身份和关系识别可信度；不得主动扫描或注入测试流量。
- **FR-017**: 系统 MUST 在观察到新设备或控制器访问变化时更新相关资产/拓扑记录，并记录触发事件及时间。
- **FR-018**: 系统 MUST 在拓扑/资产视图中呈现有数据支持的健康状态和通信质量状态，并以颜色加文本或图标说明状态；数据不完整或未知时不得显示为健康。
- **FR-019**: 系统 MUST 展示目标交换机提供的端口运行状态和相关流量/错误计数器，标注计数来源；平台不提供的指标 MUST 标记为不可用。
- **FR-020**: 系统 MUST 允许管理员指定基线观察窗口，并根据窗口内有效的通信质量数据生成可检查和调整的告警阈值；基线不完整时 MUST 阻止阈值建议自动启用。
- **FR-021**: 系统 MUST 生成可供用户查看或导出的验收/诊断报告，包含监测范围、时间窗口、资产/拓扑摘要、质量指标、事件依据和观测完整性。
- **FR-022**: 系统 MUST 允许管理员配置 MQTT 告警目标并发送告警摘要，至少包含事件类别、时间、关联设备/关系、可信状态和证据摘要；连接 MUST 使用 TLS 加密并进行代理身份认证；认证凭据 MUST 安全保存且不得在界面或日志中明文暴露；系统 MUST 显示发送失败状态并保留本地事件。
- **FR-023**: 系统 MUST 显示设备时间同步状态；质量趋势、拓扑事件、告警和报告 MUST 使用一致的观测时间基准，并在时间基准不稳定时标记受影响数据。
- **FR-024**: 系统 MUST 在资产详情中展示该设备各个有有效样本的通信关系抖动统计及样本覆盖范围；样本不可用时 MUST 显示原因。
- **FR-025**: 系统 MUST 对可解析的周期性 PROFINET 流量展示按设备或关系统计的观察刷新周期/刷新率及测量窗口；无法可靠估算时 MUST 标为不可用。
- **FR-026**: 分析模块 MUST 安全解析最多 4 层 VLAN 标签、IPv4/IPv6、TCP/UDP 头及长度边界；IPv4/IPv6 分片、截断头和不支持的扩展头 MUST 保留部分/不可解析状态，不得误当作完整传输层报文。
- **FR-027**: 对支持的 TCP 应用协议，系统 MUST 按方向跟踪 TCP 序号、确认号、窗口、SYN/FIN/RST、可解析的 TCP 选项、重复 ACK、序号缺口候选、重传候选、乱序和 ACK 超时候选；时延/超时结论 MUST 标明观测范围与可信状态。
- **FR-028**: 系统 MUST 在有界内存内对 TCP 载荷进行连续/乱序重组，再按应用协议 PDU 长度边界解码；缓存或 PDU 超出配置上限时 MUST 标记重组溢出/不完整，不得静默拼接或误识别。
- **FR-029**: 交换机宿主 MUST 能声明监测范围的方向/路径覆盖完整性；覆盖为未知或不完整时，TCP 序号缺口 MUST 作为“未捕获/原因不确定”呈现，不得报告为确认网络丢包。只有镜像范围已明确覆盖双向完整路径时，才可将其呈现为已确认的捕获序号缺口，且仍须与网络丢包区分。
- **FR-030**: 宿主 MUST 能通过模块对外 API 查询 TCP 流诊断快照；快照 MUST 含 VLAN/IP/端口、序号/确认号分析计数、应用协议分类和观测完整性，但 MUST NOT 暴露或持久化重组缓存中的应用载荷。
- **FR-031**: 宿主 MUST 能查询有界 TCP 流跟踪器的当前流数量、因容量限制而拒绝的新流数量及当前 RTO 配置，使流诊断结果可显式标识容量不完整。

### Key Entities *(include if feature involves data)*

- **监测范围**：用户选择或设备配置的面板端口及协议观测范围，以及当前采集可用状态。
- **通信端点**：被观察到参与 OT 通信的设备标识和地址信息，以及识别可信度。
- **通信关系**：按协议、源端点、目标端点及可用业务标识归纳的通信往来。
- **业务类别**：协议内可识别的业务或服务分类，以及对应报文数、字节数和占比。
- **通信质量样本**：特定通信关系与时间范围内的时延、抖动、丢包/超时和校验统计及各自计算口径。
- **异常事件**：观察到的异常类别、时间、关联对象、次数、判定依据和可信状态。
- **观测状态**：复制流量覆盖、CPU 采集能力、解析完整性、时间基准和统计连续性的状态信息。
- **保存策略**：汇总指标和异常事件的保留天数；默认值为 7 天，可由用户设置为更长时长。
- **用户权限**：交换机账户在 OT 分析功能中的查看或管理员权限，用于控制结果访问和设置修改。
- **OT 资产/拓扑**：从被动报文和交换机端口状态观察到的设备、端口和通信关系及其身份可信度。
- **通信基线**：管理员指定时间窗内的有效通信质量数据及据此生成、可检查和调整的告警阈值。
- **诊断/验收报告**：指定监测范围和时间窗的资产、质量、事件和观测完整性摘要。
- **MQTT 告警目标**：管理员配置的告警消息目标、TLS/代理身份认证状态及其可达/发送状态；凭据由交换机安全凭据管理机制保护。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对含两种受支持协议的验收流量，工程师可在 1 分钟内找到指定端点或通信关系的流量概况。
- **SC-002**: 对具备完整双向样本的验收通信，展示的往返时延与独立参考结果偏差不超过 1 个采集时间分辨单位或参考值的 5%，取较大者。
- **SC-003**: 在包含已知超时、序列缺口及可观察校验错误的验收数据中，系统对每类可见事件的分类和计数均与参考结果一致；不可见信息标为不可用或不确定。
- **SC-004**: 对包含已知协议业务类别的验收数据，已识别类别的报文数和字节数与参考结果一致，未识别报文不会并入已识别类别。
- **SC-005**: 运维人员能够通过协议、端点、通信关系和时间范围筛选，从概览进入异常详情，并在 3 次交互内定位到相关事件。
- **SC-006**: 当观测数据不足或受限时，所有受影响的通信质量结论均显示原因或可信状态，避免把未知状态呈现为确认正常。
- **SC-007**: 新安装或恢复默认配置时，汇总指标和异常事件保存时长为 7 天；用户设置更长时长后，界面显示该时长，且该保留期内的数据可供查询。
- **SC-008**: 具有查看权限的用户可以查看 OT 分析结果和设置，但无法修改监测及保存设置；管理员可以修改这些设置。
- **SC-009**: 对所有在参考流量和交换机端口数据中可识别的设备、端口和通信关系，拓扑视图均展示对应实体或明确的未知状态；拓扑健康状态与关系质量数据的状态相符。
- **SC-010**: 完整基线窗口生成的每个告警阈值都可追溯至观察窗口和指标数据；不完整窗口不会自动启用阈值。
- **SC-011**: 验收/诊断报告覆盖所选时间窗口内的质量数据与事件，MQTT 告警状态能反映发送尝试和 broker 接收确认；失败时本地事件仍可查看。
- **SC-012**: 对具有有效抖动样本的每个验收设备，资产详情都能查看对应关系的抖动统计和时间覆盖；缺少有效样本的设备明确标记不可用。
- **SC-013**: 对参考样本中可解析且周期稳定的 PROFINET 设备，详情显示的刷新周期/刷新率与样本参考值一致；其余设备显示不可用或数据不足。
- **SC-014**: MQTT 验收中，告警客户端仅通过 TLS 加密连接到经过身份认证的消息代理；凭据在界面和日志中均不可见，连接或认证失败时状态可见且本地事件保留。
- **SC-015**: 对含 0–4 层 VLAN、IPv4/IPv6、TCP/UDP、IP 分片和截断头的参考帧，模块均能提取正确可见元数据或返回明确的部分/不可解析状态；不完整头部不会触发越界读取。
- **SC-016**: 对跨 TCP 分段、乱序补齐、重传及确认超时的参考会话，模块能在声明的缓冲上限内重组协议 PDU 并输出对应诊断；将镜像覆盖设为单向/未知后，序号缺口和超时保持观测候选，不会显示为确认网络丢包。

## Assumptions

- 产品使用交换机 ACL/镜像机制将面板端口流量复制到 CPU；复制策略、端口选择和硬件能力由交换机平台提供。
- 用户希望观测的是交换机可见的被动流量，分析软件不修改、注入或阻断 OT 通信。
- OT 分析功能复用交换机现有账户和权限，不引入独立账户体系。
- v1 的“业务内容分布”指可识别协议业务/服务类别和通信元数据的统计，不包括任意原始应用载荷的内容检查、解密或长期保存。
- 默认将往返时延作为可从被动双向复制流量计算的时延口径；单向时延需要额外时间同步条件，不作为默认承诺。
- 丢包是基于可观察协议行为或序列信息推断的指标；仅凭某报文未出现在 CPU 复制流量中，无法确认其在交换网络中丢失。
- 校验失败统计范围受交换芯片转发和复制路径限制；捕获路径未暴露的物理层/FCS 错误不能由软件推断为零。
- 受支持协议的业务类别以当前可解析且可见的协议字段为限；TLS、OPC UA 加密内容、厂商私有或不完整字段可列为加密/未识别/不完整，不对应用载荷解密。
- TCP 应用 PDU 在有界的每方向序号窗口内重组；缺片、超出缓存上限或捕获从会话中途开始时，解析状态应保留为部分/未解析，不将单帧解码等同于完整会话。
- TCP 观测可能因 ACL 镜像策略、镜像端口选择、CPU 丢弃或只覆盖单向路径而缺失；序号跳跃首先是捕获范围中的“未见数据”证据，不能单独证明交换网络丢包。
- 具体设备型号的最大监测端口数、最大报文速率和更长保存时长的可用上限属于平台约束，需要结合硬件存储与负载能力确定。
- 拓扑发现仅使用被动流量和交换机可提供的端口/资产信息；不会主动扫描 IT/OT 网络或执行会影响控制通信的诊断操作。
- 基线阈值建议依据管理员指定的有效观察窗口生成；特定指标的统计方法在计划阶段定义，并允许管理员检查和调整。
- MQTT 告警目标必须使用 TLS 和代理身份认证；凭据管理复用交换机的安全凭据存储能力，不在普通配置、界面或日志中明文呈现。
